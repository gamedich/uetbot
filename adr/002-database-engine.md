# ADR 002: Выбор СУБД — Встраиваемая база данных SQLite3 в режиме WAL против PostgreSQL

- **Статус:** Принято (Accepted)
- **Дата:** 2025-10-18
- **Автор:** Главный архитектор проекта (Principal Architect)
- **Область действия:** Слой хранения данных (Data Storage Layer) АИС «УЭТ-Бот»
- **Стандарт:** Architecture Decision Records (Michael Nygard format)

---

## Контекст и проблематика

МУП «Ульяновскэлектротранс» эксплуатирует автоматизированную систему для решения задач подбора персонала (водителей, кондукторов, ремонтников) и сервисного информирования. Прогнозируемый объем данных составляет от 5 000 до 50 000 анкет соискателей в год с сопутствующими метаданными (логи согласий по 152-ФЗ, аудит-логи, журналы собеседований и расписание депо).

Ключевые эксплуатационные и инфраструктурные ограничения заказчика:
1. **Простота развертывания и автономность (Zero Administration):** Серверы предприятия администрируются ограниченным штатом системных инженеров. Требуется исключить сложные распределенные кластеры, требующие непрерывного мониторинга сетевых портов, вакуумирования и сложного резервного копирования.
2. **Надежность и атомарность (ACID):** Каждая анкета соискателя и отзыв согласия на обработку ПДн должны сохраняться с гарантией недопущения повреждения данных при внезапном отключении электропитания.
3. **Безопасность и изоляция (152-ФЗ):** База данных не должна иметь открытых сетевых сокетов (портов TCP/IP), доступных для сканирования из внутренней сети или интернета.
4. **Легковесность тестовой среды (12-Factor App):** Тестовый контур и пайплайн CI/CD должны запускаться за считанные секунды без поднятия тяжелых Docker-контейнеров с внешними СУБД.

---

## Рассмотренные альтернативы

### Альтернатива 1: Клиент-серверная СУБД PostgreSQL
- *Преимущества:* Промышленный стандарт для высоконагруженных систем (Highload), встроенные механизмы параллельной репликации, развитая система транзакций, мощные возможности JSONB.
- *Недостатки:* Избыточная сложность инфраструктуры для текущего профиля нагрузки (сотни запросов в минуту, а не сотни тысяч). Необходимость сопровождения отдельного демона `postgresql`, управления пулом сетевых соединений (PgBouncer), мониторинга потребления ОЗУ и сетевой безопасности. Существенное замедление выполнения пирамиды тестов (поднятие тестовой БД в Docker занимает 10-20 секунд против нескольких миллисекунд у SQLite `:memory:`).

### Альтернатива 2: NoSQL документная база (MongoDB / Redis как основное хранилище)
- *Преимущества:* Гибкая схема документа для анкеты соискателя, высокая скорость вставок.
- *Недостатки:* Слабая поддержка транзакционной целостности на уровне реляционных связей, сложность обеспечения строгих внешних ключей (Foreign Keys) между кандидатами, администраторами и актами уничтожения по 152-ФЗ. Несоответствие регламентам госзаказа и требованиям к традиционным муниципальным АИС.

### Альтернатива 3: SQLite3 в режиме WAL с контекстными менеджерами (Выбранное решение)
- *Преимущества:* Встраиваемая (embedded) реляционная СУБД без сетевых оверхедов. Нативная поддержка режима журнала с упреждающей записью (Write-Ahead Logging, WAL), обеспечивающая параллельное чтение несколькими потоками без блокировки пишущего потока. Идеальная переносимость (вся база в одном файле `resumes.db`), нулевое администрирование, встроенный API онлайн-бэкапов без остановки сервиса.

---

## Архитектурное решение

Принято решение утвердить **SQLite3 в режиме WAL (`PRAGMA journal_mode=WAL;`) с принудительным контролем внешних ключей (`PRAGMA foreign_keys=ON;`) и управлением транзакциями через контекстные менеджеры** в качестве основного движка базы данных АИС «УЭТ-Бот».

Ключевые проектные решения слоя хранения:
1. **Режим WAL (Write-Ahead Logging):** Позволяет неограниченному числу читателей (веб-панель, Telegram-хэндлеры расписания) параллельно считывать данные во время выполнения операций записи новыми соискателями.
2. **Потокобезопасность и пул (Thread-local caching):** Класс `ResumeDB` реализует потокобезопасное кэширование соединений `threading.local()` с таймаутом ожидания блокировки до 30.0 секунд, полностью исключая ошибки `database is locked`.
3. **Безопасные транзакции (Context Managers):** Использование паттерна `with self.connection() as conn:` гарантирует автоматический вызов `conn.commit()` при успешном завершении блока и немедленный `conn.rollback()` при возникновении любого необработанного исключения.
4. **Абсолютная изоляция сред (12-Factor App):** Путь к базе передается через переменную окружения `DB_PATH`. В тестах используется сверхбыстрая база в оперативной памяти (`:memory:`) или временный изолированный файл `tmp_path`, что обеспечивает 100% изоляцию тестов от прод-данных.
5. **Горячее резервное копирование (Online Backup API):** Создание снапшотов БД на лету через `sqlite3.Connection.backup()` каждые 6 часов без простоя сервиса.

## Последствия (Consequences)

### Положительные последствия:
- **Нулевая стоимость сопровождения:** Отсутствует необходимость нанимать или привлекать штатного администратора баз данных (DBA).
- **Максимальная безопасность:** База хранится в файле с правами `0600` на сервере. Вектор атак через сетевой протокол СУБД полностью ликвидирован.
- **Молниеносные тесты:** Полный прогон более 40 тестов пирамиды тестирования Pytest выполняется менее чем за 5 секунд.

### Ограничения и стратегия эволюции:
- *Ограничение:* SQLite ограничен одним пишущим процессом (Single-writer).
  *Оценка применимости:* Для муниципального сервиса рекрутинга с интенсивностью до 10-20 анкет в минуту однопоточная запись в режиме WAL обеспечивает запас производительности свыше 1500%.
- *План миграции (при необходимости):* Слой доступа к данным абстрагирован через миксины репозиториев (`CandidateMixin`, `AdminMixin`, `InquiryMixin`). В случае превышения нагрузки 100 000 анкет в месяц репозитории могут быть прозрачно переведены на PostgreSQL через SQLAlchemy/Asyncpg без модификации бизнес-логики хэндлеров.
