# ADR 002: Архитектура базы данных и пула соединений (SQLite с WAL-режимом)

* **Статус:** Принято (Accepted)
* **Дата:** 2026-08-15
* **Автор:** Senior DevOps / Tech Lead МУП «Ульяновскэлектротранс»

## Контекст и проблематика
Для хранения расписаний, обращений пассажиров, состояний FSM и анкет соискателей требовалось выбрать СУБД. Условия эксплуатации:
- Развертывание на автономном виртуальном сервере предприятия без избыточных накладных расходов на администрирование внешних СУБД.
- Строгие требования 152-ФЗ: локальное хранение данных в пределах защищенного контура без передачи третьим сторонам.
- Необходимость исключения блокировок `database is locked` при одновременной записи откликов и чтении расписаний.
- Надежность: защита от сбоев питания и повреждения таблиц (zero data loss).

Рассматривались альтернативы:
1. **PostgreSQL:** промышленная СУБД с отличной поддержкой параллелизма, но избыточна по потреблению ресурсов для текущего масштаба (требует отдельного демона, настроек pg_hba, регулярного вакуума и бэкапов pg_dump).
2. **MongoDB / NoSQL:** гибкая схема документов, но отсутствие строгих реляционных связей и нарушение требований к структурированному архивированию ПДн.
3. **Встраиваемая SQLite в режиме по умолчанию (Rollback Journal):** минимальное потребление ресурсов, но блокирует базу целиком при любой операции записи.
4. **SQLite в режиме WAL (Write-Ahead Logging) с пулом соединений и PRAGMA-оптимизацией.**

## Решение
Принять **SQLite** в качестве основной базы данных с обязательной инициализацией в режиме **WAL (Write-Ahead Logging)** и архитектурой пула соединений через контекстные менеджеры `with self.connection()`.

### Реализованные архитектурные и технические решения:
1. **Режим WAL (Write-Ahead Logging):**
   - Выполняется `PRAGMA journal_mode = WAL;`. Записи ведутся в файл `resumes.db-wal`, позволяя неограниченному числу читателей работать параллельно с пишущей транзакцией.
2. **Оптимизация производительности и целостности:**
   - `PRAGMA synchronous = NORMAL;` — гарантирует устойчивость к сбоям приложений при максимальной скорости I/O.
   - `PRAGMA busy_timeout = 60000;` — ожидание освобождения блокировки до 60 секунд вместо выброса ошибки `sqlite3.OperationalError: database is locked`.
   - `PRAGMA foreign_keys = ON;` — строгий контроль внешних ключей и каскадное удаление.
   - `PRAGMA temp_store = MEMORY;` — хранение временных таблиц в ОЗУ.
   - `PRAGMA cache_size = -64000;` — выделение 64 МБ кэша страниц в оперативной памяти.
3. **Пул соединений и управление дескрипторами:**
   - Каждое обращение к БД обернуто в контекстный менеджер с автоматическим закрытием дескрипторов курсора и соединения, исключая утечки дескрипторов файлов в Linux (`lsof`).
   - Изоляция боевой (`resumes.db`) и тестовой (`test_resumes.db`) баз данных через фабрику подключений.

## Последствия (Consequences)

### Положительные:
- Полное устранение ошибок `database is locked` при пиковых нагрузках до 100 одновременных RPS.
- Скорость чтения расписаний < 1 мс.
- Удобство создания мгновенных атомарных резервных копий через `sqlite3_backup` (раздел «Управление бэкапами»).
- Компактность: единый файл базы данных легко шифруется и архивируется по ГОСТ.

### Отрицательные / Риски:
- Ограничение на распределенную горизонтальную масштабируемость (Single-node). При росте предприятия до десятков миллионов записей потребуется миграция на PostgreSQL.
