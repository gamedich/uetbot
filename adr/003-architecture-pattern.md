# ADR 003: Архитектурный шаблон — Многоуровневая модульная архитектура (Layered Modular Architecture)

- **Статус:** Принято (Accepted)
- **Дата:** 2025-10-20
- **Автор:** Главный архитектор проекта (Principal Architect)
- **Область действия:** Общая структура кодовой базы и разделение ответственности в АИС «УЭТ-Бот»
- **Стандарт:** Architecture Decision Records (Michael Nygard format)

---

## Контекст и проблематика

Типичной анти-паттерном разработки ботов для мессенджеров является «толстый обработчик» (Fat Handler / Smart UI), при котором логика приема сообщения, разбор текста, валидация полей, формирование SQL-запросов к базе данных, отправка ответов и логирование смешиваются внутри единой асинхронной функции.

В проекте МУП «Ульяновскэлектротранс» такая архитектура недопустима по следующим причинам:
1. **Сложная нормативная база:** Валидация возраста кандидатов регулируется ст. 26 196-ФЗ и ст. 328.1 ТК РФ, расчет надбавок за ночные смены — ст. 154 ТК РФ, защита данных — 152-ФЗ. Бизнес-правила должны быть изолированы и тестироваться независимо от сетевого контекста Telegram.
2. **Омниканальность:** Система должна поддерживать прием анкет через Telegram-бота, веб-форму Telegram Mini App, шлюз социальной сети ВКонтакте и корпоративный мессенджер МАКС. Дублирование валидации и бизнес-логики в каждом канале порождает расхождения и дефекты.
3. **Поддерживаемость и тестируемость:** Код должен укладываться в классическую пирамиду тестирования (Unit -> Integration -> E2E) без необходимости мокировать сетевые пакеты Telegram в юнит-тестах.

## Рассмотренные альтернативы

### Альтернатива 1: Монолитные обработчики с процедурным кодом (Script/Handler Monolith)
- *Преимущества:* Быстрый старт прототипа на ранних этапах.
- *Недостатки:* Нулевая тестируемость. Любое изменение в тексте сообщения ломает логику сохранения в БД. Невозможность повторного использования логики в шлюзах VK/MAX и WebApp.

### Альтернатива 2: Микросервисная архитектура (Microservices)
- *Преимущества:* Независимое масштабирование сервиса анкетирования, сервиса расписаний и сервиса документооборота.
- *Недостатки:* Колоссальный инфраструктурный оверхед для муниципального проекта. Необходимость настройки Service Discovery, брокеров сообщений (RabbitMQ/Kafka), координации распределенных транзакций и усложнение отладки для локального сервера предприятия.

### Альтернатива 3: Многоуровневая модульная архитектура (Layered Modular Architecture — Выбранное решение)
- *Преимущества:* Четкое разделение ответственности (Separation of Concerns). Сквозной поток данных проходит через строго определенные изолированные слои: Транспортный уровень (Routers/Gateways) -> Уровень состояний (FSM) -> Сервисный слой доменной логики (Core Services) -> Слой доступа к данным (DAO / Repositories).

---

## Архитектурное решение

Принято решение утвердить **Многоуровневую модульную архитектуру (Layered Modular Architecture)** в качестве базового проектного стандарта АИС «УЭТ-Бот».

### Спецификация слоев архитектуры:

```
[Пользовательский интерфейс: Telegram / VK / WebApp]
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│ 1. Транспортный слой / Обработчики (Routers & Handlers) │
│    - handlers/candidate.py, handlers/admin.py          │
│    - Прием событий, фильтрация команд, отправка UI    │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│ 2. Слой состояний и диалогов (FSM Engine)              │
│    - common.py:CandidateForm, InquiryForm              │
│    - Управление цепочкой 16 шагов анкетирования        │
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│ 3. Сервисный слой доменной логики (Core Domain Services)│
│    - services/domain_rules.py, services/candidate_svc. │
│    - Валидация ФИО, телефонов, 196-ФЗ (21+), расчет смен│
└────────────────────────┬───────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────────────┐
│ 4. Слой доступа к данным (DAO / Repositories / DB)     │
│    - repositories/candidate_repo.py, database.py       │
│    - Параметризованный SQL, транзакции, режим WAL      │
└────────────────────────────────────────────────────────┘
```

1. **Слой роутеров и обработчиков (Routers/Handlers):**
   Отвечает исключительно за парсинг входящих сообщений/колбэков, проверку прав через middleware и вызов сервисного слоя. Не содержит прямых SQL-запросов.
2. **Слой состояний (FSM Layer):**
   Управляет шагами опросника соискателя (`CandidateForm`). Хранит промежуточное состояние в персистентном или in-memory хранилище. По завершении диалога передает агрегированный словарь данных в сервисный слой и очищает контекст (`state.clear()`).
3. **Сервисный слой доменной логики (Domain Services):**
   Центральное ядро («чистая архитектура»). Модуль `services/domain_rules.py` содержит чистые (pure) функции без побочных эффектов: `validate_russian_fio`, `validate_phone_number`, `validate_candidate_age_for_role`, `calculate_shift_pay`. Данный слой тестируется на 100% изолированными юнит-тестами.
4. **Слой репозиториев (Data Access Object / Repository):**
   Модули `repositories/` инкапсулируют взаимодействие с реляционной СУБД SQLite. Реализуют атомарные транзакции, миграции и параметризованные запросы.

## Последствия (Consequences)

### Положительные последствия:
- **Высокая тестируемость:** Доменная бизнес-логика тестируется в изоляции за миллисекунды (`tests/test_unit.py`), база данных тестируется в `:memory:` (`tests/test_integration.py`), а сквозной диалог проверяется в `tests/test_e2e.py`.
- **Омниканальность без дублирования:** Шлюз Telegram и шлюз ВКонтакте вызывают одни и те же методы `CandidateService.register_candidate()`, гарантируя одинаковые правила валидации и синхронизацию данных.
- **Низкая связанность (Low Coupling):** Изменение схемы базы данных не требует правок в клавиатурах Telegram, а редизайн текстов сообщений не затрагивает формулы расчета заработной платы.
