# ADR 004: Стратегия ветвления Git и управление жизненным циклом релизов (Git Branching Strategy)

* **Статус:** Принято (Accepted)
* **Дата:** 2026-08-25
* **Автор:** Senior DevOps / Application Security Engineer / Tech Lead МУП «Ульяновскэлектротранс»

## 1. Контекст и проблематика
При разработке и сопровождении критически важной информационной системы городского электрического пассажирского транспорта МУП «Ульяновскэлектротранс» (UETBot) требуется надежная, предсказуемая и безопасная стратегия версионирования исходного кода. Система обслуживает тысячи ежедневных пассажиров, диспетчерскую службу движения и кадровый департамент предприятия. Любой сбой в коде на боевом сервере может привести к дезинформации жителей о движении трамваев и троллейбусов, срыву расписания или утечке персональных данных кандидатов по 152-ФЗ.

Ранее в репозитории наблюдались стихийные коммиты напрямую в основную ветку, а также присутствовали опасные механизмы исполнения `git pull`, `git checkout` и `git reset` непосредственно из рантайма Telegram-бота через команду `/git` и веб-интерфейс. Подобная практика несет критические риски информационной безопасности:
1. Возможность удаленного выполнения произвольного кода (RCE) при компрометации токена бота или сессии веб-панели.
2. Невозможность проведения контролируемого статического анализа и тестов перед деплоем на сервер.
3. Риск рассинхронизации локальной базы данных SQLite при внезапном откате коммитов в рантайме.

Для обеспечения стабильности, выполнения требований стандартов МДК 03.03 (Трек B) и корпоративной безопасности предприятия возникла необходимость утвердить регламентированную стратегию ветвления, защиты веток и развертывания.

---

## 2. Сравнительный анализ альтернатив

### Вариант 1: Классический GitFlow
- **Плюсы:** Полная изоляция веток разработки (`develop`), релизов (`release/*`), горячих исправлений (`hotfix/*`) и мастера (`master`).
- **Минусы:** Избыточная сложность и бюрократизация для команды из 3–5 разработчиков, задержки в выпуске срочных оповещений об изменениях маршрутов, частые конфликты слияния при синхронизации `develop` и `master`.

### Вариант 2: Trunk-Based Development
- **Плюсы:** Максимальная скорость интеграции, коммиты напрямую в `main` малыми порциями под Feature Flags.
- **Минусы:** Высокий риск попадания нетестированного кода на прод в условиях отсутствия круглосуточного конвейера автоматического канареечного развертывания (Canary deployment) на муниципальном сервере.

### Вариант 3: Модифицированный GitHub Flow с ветками `main`, `beta`, `release/*` и `hotfix/*` (Выбранное решение)
- Оптимальный баланс между безопасностью и скоростью доставки ценности. Включает строгую защиту ветки `main`, постоянную тестовую среду `beta`, релизные срезы для стабилизации и регламент горячих исправлений.

---

## 3. Принятое решение

Утвердить **Модифицированный GitHub Flow с двухуровневым контуром веток** в качестве официального стандарта версионирования репозитория проекта UETBot:

```
[hotfix/db-descriptor-fix] ──────────┐
                                     ▼
[feature/...] ──► [beta] ──► [release/v1.8.0] ──► [main] (Production 100% SLA)
                    ▲
    (Автотесты CI,  │
     Staging стенд) └── [Pull Request + Code Review]
```

### 3.1. Структура и роли веток:

1. **Ветка `main` (Production Contour):**
   - Эталонная стабильная версия системы. Код в этой ветке всегда готов к работе на боевом сервере МУП «УЭТ».
   - Прямые пуши (`git push origin main`) строго **запрещены** правилами Branch Protection.
   - Изменения попадают в `main` исключительно через Pull Request из веток `release/*` или `hotfix/*` после прохождения всех проверок автоматического пайплайна CI/CD и подтверждения от Tech Lead / SecOps.
   - Каждый коммит в `main` сопровождается аннотированным Git-тегом версии по стандарту SemVer (например, `v1.8.0`).

2. **Ветка `beta` (Staging & Integration Contour):**
   - Интеграционная ветка закрытого тестирования. Развернута на предбоевом стенде с тестовой базой данных `test_resumes.db`.
   - Ветка используется для комплексного сквозного тестирования новых функций диспетчеризации, валидации FSM-анкеты и Mini App перед релизом.
   - Слияние веток функций (`feature/*`) осуществляется в `beta` через Pull Request.

3. **Ветки функций (`feature/<kebab-case-name>`):**
   - Создаются от актуального состояния ветки `beta`.
   - Именуются в строгом соответствии с назначением:
     - `feature/route-schedule-fsm`
     - `feature/passenger-feedback`
     - `feature/dispatcher-alerts`
     - `feature/sqlite-wal-optimization`
     - `feature/docs-mkdocs`
   - После реализации задачи и прохождения локальных проверок открывается PR в ветку `beta`. После успешного ревью и слияния ветка функции удаляется.

4. **Релизные ветки (`release/vX.Y.Z`):**
   - Создаются от `beta`, когда накоплен объем функций для очередной плановой версии (например, `release/v1.8.0`).
   - На релизной ветке проводятся исключительно стабилизационные правки, обновление документации, проверка CHANGELOG.md и финальный аудит зависимостей.
   - После стабилизации релизная ветка вливается через PR в `main` (с проставлением тега `v1.8.0`) и обратно в `beta`.

5. **Ветки горячих исправлений (`hotfix/<kebab-case-name>`):**
   - Создаются напрямую от ветки `main` при обнаружении критических дефектов на проде (утечки дескрипторов БД, блокировки WAL, сбои авторизации Telegram API).
   - Пример: `hotfix/db-descriptor-fix`.
   - Вливаются по ускоренной процедуре через PR с наивысшим приоритетом одновременно в `main` и в `beta`.

## 4. Стандарт сообщений коммитов (Conventional Commits)

Все коммиты в репозитории обязаны строго следовать спецификации **Conventional Commits 1.0.0**:

```
<тип>(<область>): <краткое описание в повелительном наклонении>

[необязательное подробное тело коммита]

[необязательный подвал с BREAKING CHANGE и ссылками на тикеты]
```

### Разрешенные типы коммитов:
- `feat`: добавление новой функциональности для пассажиров или диспетчеров.
- `fix`: исправление ошибки в существующей логике.
- `docs`: обновление нормативной документации, PRD, ADR или руководств.
- `style`: исправления форматирования кода (Black, Ruff), не влияющие на логику.
- `refactor`: переработка структуры кода без изменения внешнего поведения.
- `perf`: оптимизация производительности (индексы SQLite, кэширование).
- `test`: добавление или исправление автоматических тестов.
- `chore`: рутинные задачи сборки, обновление зависимостей или скриптов деплоя.
- `security`: закрытие уязвимостей, изоляция секретов, аудит безопасности.

При наличии обратной несовместимости в футере или заголовке коммита указывается явная метка `BREAKING CHANGE:` с подробным описанием причин и инструкцией по миграции.

## 5. Изоляция административного контура и регламент деплоя

В соответствии с требованиями информационной безопасности МУП «УЭТ»:
1. **Полное удаление команд Git из приложения:** Из рантайма бота и обработчиков веб-панели навсегда удалены вызовы `subprocess`, `os.system("git ...")` и команда `/git`. Бот работает от непривилегированного пользователя операционной системы без доступа к бинарнику `git` в контексте веб-демона.
2. **Деплой только по SSH:** Переключение веток (`main` / `beta`), подтягивание изменений из GitHub и перезапуск системной службы `uet_bot.service` выполняются исключительно администратором сервера по защищенному SSH-каналу с аутентификацией по ed25519-ключам.
3. **Автономный скрипт развертывания:** Для безопасной процедуры обновления оформлен локальный скрипт `deploy/server_switch_branch.sh` с правами доступа `700` (`rwx------`), находящийся вне публичного Git-дерева. Скрипт проводит предварительную проверку чистоты рабочего дерева, валидацию байткода Python (`compileall`) и верификацию статуса systemd.

## 6. Последствия (Consequences)

### Положительные:
- Полное устранение вектора RCE-атак через Telegram-бота и публичную веб-консоль.
- Прозрачная история изменений: каждый коммит понятен аудиторам и соответствует стандарту Keep a Changelog.
- Гарантия непрерывной работоспособности продакшн-контура со строгим соблюдением SLA 99.5%.
- Четкое разделение ответственности: разработчики работают в ветках `feature/*`, тестировщики проверяют `beta`, релиз-инженеры выводят `main`.

### Отрицательные:
- Необходимость совершать деплой через защищенный терминал SSH вместо нажатия кнопки в мессенджере. Это осознанный выбор в пользу бескомпромиссной безопасности и надежности пассажирского транспорта.
