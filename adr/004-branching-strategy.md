# ADR 004: Стратегия ветвления и регламент коммитов — Git Flow / Trunk-based с Conventional Commits

- **Статус:** Принято (Accepted)
- **Дата:** 2025-10-25
- **Автор:** Главный архитектор проекта (Principal Architect)
- **Область действия:** Процессы разработки, CI/CD и версионирования АИС «УЭТ-Бот»
- **Стандарт:** Architecture Decision Records (Michael Nygard format)

---

## Контекст и проблематика

АИС «УЭТ-Бот» является критически важным сервисом кадрового обеспечения муниципального перевозчика. Одновременно с эксплуатацией боевого контура (ветка `main`, порт 8080, бот `@uet_job_bot`) ведется активная разработка новых функциональных возможностей:
- Интеграция с корпоративным мессенджером МАКС (VK Teams);
- Поддержка новых моделей подвижного состава (троллейбусы с автономным ходом);
- Развитие личного кабинета сотрудников депо.

Беспорядочный коммит изменений непосредственно в рабочую ветку чреват нарушением работоспособности бота в часы пик и срывом приема анкет. Требуется строгая, прозрачная и автоматизированная модель управления версиями, ветвлением и документированием изменений.

---

## Рассмотренные альтернативы

### Альтернатива 1: Классический тяжеловесный Git Flow
- *Преимущества:* Строгое разделение веток `develop`, `release/*`, `hotfix/*`, `feature/*`, `master`.
- *Недостатки:* Избыточная бюрократия для компактной инженерной команды (2-4 разработчика). Частые конфликты при слиянии долгоживущих веток релизов, задержки с доставкой критических хотфиксов.

### Альтернатива 2: Неструктурированный Trunk-Based Development (коммиты прямо в main)
- *Преимущества:* Минимальные накладные расходы.
- *Недостатки:* Высокий риск дестабилизации продакшена. Невозможность проведения изолированного тестирования бета-версий заказчиком на реальном сервере до выкатки на сотни соискателей.

### Альтернатива 3: Адаптированный Git Flow (Main + Beta/Develop) со стандартом Conventional Commits (Выбранное решение)
- *Преимущества:* Сбалансированный подход. Стабильная производственная ветка `main` (Прод, порт 8080) и выделенная интеграционная ветка `beta` (Стенд приемочного тестирования, порт 8082). Каждая функциональная доработка оформляется в короткоживущей feature-ветке. Все коммиты строго соответствуют стандарту Conventional Commits, что обеспечивает автоматическую генерацию `CHANGELOG.md` и валидацию версий SemVer.

---

## Архитектурное решение

Принято решение утвердить **Адаптированную стратегию Git Flow (Ветки `main` и `beta`) с обязательным соблюдением спецификации Conventional Commits 1.0.0 и Semantic Versioning (SemVer 2.0.0)**.

### 1. Топология веток репозитория

```
[feature/xxx] ────┐ (Pull Request + CI)
                  ▼
[beta]   ─────────●───────●───────● (Тестовый стенд: uet_bot_beta.service, порт 8082)
                          │
                          ▼ (Release Tag vX.Y.Z)
[main]   ─────────────────●───────● (Боевой контур: uet_bot.service, порт 8080)
```

1. **Ветка `main` (Production):**
   - Содержит только стабильные, прошедшие полное тестирование и аудит релизы.
   - Прямой `push` в `main` заблокирован (защита веток).
   - Развертывание осуществляется в `/home/botuser/uetbot` под управлением `uet_bot.service`.
2. **Ветка `beta` (Staging / Acceptance Testing):**
   - Интеграционная ветка для проверки новых функций сотрудниками службы кадров МУП «УЭТ».
   - Развертывание осуществляется в `/home/botuser/uetbot2` под управлением `uet_bot_beta.service`.
3. **Ветки `feature/*` и `fix/*`:**
   - Ответвляются от `beta`, живут не более 3-5 дней и сливаются обратно через Pull Request после успешного прогона 40+ тестов Pytest.

### 2. Спецификация сообщений коммитов (Conventional Commits)

Все сообщения коммитов должны строго следовать шаблону:
`<type>(<scope>): <short description>`

Допустимые типы изменений (`type`):
- `feat`: Новая функциональность для пользователя или кадровой службы.
- `fix`: Исправление ошибки или бага в логике/валидаторах.
- `docs`: Изменения в документации (ТЗ, ADR, матрица трассируемости).
- `test`: Добавление новых тестов или доработка тестовой инфраструктуры.
- `refactor`: Изменение кода без изменения внешней функциональности.
- `chore`: Обновление зависимостей, pre-commit хуков, конфигураций линтеров.
- `perf`: Оптимизация производительности (SQL-индексы, кэширование).

Примеры валидных коммитов:
- `feat(fsm): add 21+ age validation for tram driver applicants`
- `fix(payroll): apply 40 percent night shift surcharge per TK RF art 154`
- `docs(gost): generate GOST 34.602-2020 technical specification`
- `test(e2e): implement end-to-end applicant registration flow`

### 3. Семантическое версионирование (SemVer 2.0.0)

Формат версии: `v<MAJOR>.<MINOR>.<PATCH>`
- `MAJOR` (v1.0.0, v2.0.0): Несовместимые изменения API или фундаментальная переработка схемы БД.
- `MINOR` (v2.1.0): Добавление новой функциональности с обратной совместимостью (новые роуты, отчеты).
- `PATCH` (v2.0.1): Обратно совместимые исправления дефектов и багов.

## Последствия (Consequences)

### Положительные последствия:
- **Полная изоляция сред:** Тестирование бета-версий кадровиками в `uetbot2` гарантированно не затрагивает живых соискателей в `uetbot`.
- **Автоматизированный аудит:** История коммитов становится машиночитаемой, позволяя автоматически генерировать журнал изменений `CHANGELOG.md` при релизах.
- **Дисциплина кода:** Использование pre-commit хуков блокирует случайное попадание приватных ключей, временных файлов и синтаксических ошибок в систему контроля версий.
