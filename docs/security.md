# Политика безопасности и модель угроз UETBot (Security Architecture)

Данный документ определяет архитектуру информационной безопасности, модель угроз, механизмы эшелонированной защиты (Defense in Depth) и правила изоляции административного контура цифровой системы МУП «Ульяновскэлектротранс».

---

## 1. Триада информационной безопасности (Модель CIA)

Архитектура системы UETBot спроектирована с учетом обеспечения трёх фундаментальных принципов:

```
           [Конфиденциальность (Confidentiality)]
                           ▲
                          / \
                         /   \
                        /     \
                       ▼       ▼
[Целостность (Integrity)] ◄───► [Доступность (Availability)]
```

### 1.1. Конфиденциальность (Confidentiality)
- **Персональные данные пассажиров и соискателей (152-ФЗ РФ):** ФИО, номера телефонов, паспортные данные и сведения о водительских удостоверениях не передаются третьим лицам и не логируются в открытом виде.
- **Хранение паролей и сессий:** Пароли администраторов хэшируются с использованием стойкого алгоритма `bcrypt` с динамической солью. Авторизация в API осуществляется через криптографически подписанные токены HMAC-SHA256 с ограниченным временем жизни (TTL).
- **Изоляция секретов:** Все токены Telegram Bot API, ключи сообщества ВКонтакте и мастер-ключи шифрования хранятся строго в переменных окружения операционной системы и файле `.env`, доступ к которому ограничен правами `0600`. Файл `.env` исключен из Git-репозитория.

### 1.2. Целостность (Integrity)
- **Параметризация SQL:** Полный запрет на использование интерполяции строк (`f"SELECT ... {user_input}"`). Все запросы к SQLite выполняются с позиционными параметрами (`?`), что на 100% исключает атаки типа SQL Injection.
- **Санитизация вывода:** Пользовательский ввод принудительно экранируется через `html.escape()` перед отправкой в Telegram, предотвращая разрушение разметки сообщений и инъекции тегов.
- **Целостность транзакций базы данных:** Использование контекстных менеджеров `with self.connection()` с обязательным откатом (`rollback()`) при возникновении любых непредвиденных исключений.

### 1.3. Доступность (Availability)
- **Высокая доступность (SLA 99.5%):** Сервис контролируется системным менеджером `systemd` с автоматическим перезапуском при аварийном завершении (`Restart=always`, `RestartSec=3`).
- **Защита от флуда и DoS/DDoS:** Ограничение частоты запросов (Rate Limiting) на уровне обратного прокси Nginx (`limit_req_zone`), встроенный антифлуд-мидлварь в aiogram и обработка исключений `TelegramRetryAfter` с экспоненциальной паузой.
- **Режим SQLite WAL (Write-Ahead Logging):** Разделение потоков чтения и записи позволяет сотням пассажиров одновременно запрашивать расписания без ожидания освобождения блокировок базы данных.

## 2. Эшелонированная защита (Defense in Depth)

Система реализует многоуровневую модель защиты:

```
Уровень 1: Сетевой периметр (Брандмауэр UFW, TLS 1.3, Nginx Reverse Proxy)
    │
Уровень 2: Операционная система (Непривилегированный пользователь, Chmod 700/600)
    │
Уровень 3: Уровень приложения (FastAPI/Aiohttp, RBAC-авторизация, Aiogram Middleware)
    │
Уровень 4: Бизнес-логика (Валидация форматов, проверка ст. 328.1 ТК РФ, White-listing)
    │
Уровень 5: Уровень данных (SQLite WAL, bcrypt, шифрование бэкапов, акты 152-ФЗ)
```

1. **Сетевой уровень:** Открыты только порты 80, 443 (Nginx) и 22 (SSH). Бэкенд aiohttp слушает только локальный сокет `127.0.0.1:8080`, прямой доступ из интернета заблокирован.
2. **Уровень ОС:** Исполняемые файлы защищены строгими правами доступа. Скрипт переключения веток `deploy/server_switch_branch.sh` имеет права `700` (`rwx------`).
3. **Уровень приложения:** Валидация прав доступа (RBAC: `superadmin`, `hr`, `tech`, `depot`, `applicant`) на уровне каждого контроллера и хэндлера.
4. **Уровень базы данных:** База размещена локально на сервере предприятия, доступ по сети исключен.

## 3. Изоляция административного контура (Критическое требование)

### 3.1. Обоснование полного исключения команд управления Git из кода бота
Ранее присутствовавшая концепция управления версиями через мессенджер (команда `/git`, стягивание обновлений `git pull`, переключение веток `git checkout` и откат `git reset --hard`) представляла собой критическую уязвимость:
1. **Угроза RCE (Remote Code Execution):** Выполнение шелл-команд через `subprocess` или `os.system` внутри веб-демона создает прямую возможность захвата хоста злоумышленником при обнаружении инъекции в аргументах.
2. **Нарушение контура аттестации ИСПДн:** Государственные и муниципальные информационные системы, обрабатывающие персональные данные (152-ФЗ), не имеют права содержать динамические механизмы неконтролируемой подмены исполняемого кода в рантайме.
3. **Человеческий фактор:** Случайное нажатие кнопки отката коммита администратором с мобильного телефона в дороге могло привести к сбросу незакоммиченных данных или остановке сервиса.

### 3.2. Архитектурное решение по изоляции
- **Полная зачистка репозитория:** В публичном коде бота на GitHub полностью удалены все хэндлеры `/git`, вызовы `_run_git_command`, кнопки меню и веб-интерфейсы синхронизации с Git.
- **Внешний вид публичного проекта:** Бот оформлен как чистый пассажирский и рекрутинговый сервис МУП «Ульяновскэлектротранс».
- **Разделение контуров:** Все операции по обновлению кода, смене веток (`main` / `beta`) и перезапуску службы вынесены исключительно в административный SSH-контур сервера:
  - Доступ по SSH разрешен только по криптографическим ключам Ed25519 (аутентификация по паролю отключена в `sshd_config`).
  - Процедура обновления выполняется через автономный локальный скрипт `deploy/server_switch_branch.sh` с предварительной компиляцией байткода (`python3 -m compileall`).
  - Файлы локальных админ-скриптов, базы данных (`*.db`, `*.sqlite*`), дампы и логи внесены в `.gitignore` и никогда не попадают в систему контроля версий.

## 4. Регламент уничтожения персональных данных (Приказ РКН №179)

При поступлении команды `/revoke` от пользователя или при принятии кадрового решения об отказе соискателю:
1. Запись кандидата безвозвратно удаляется или обезличивается в SQLite (`is_deleted = 1`, затирание ПДн нулями).
2. В таблице `destruction_acts` генерируется электронный акт с уникальным номером (формат `ACT-ГГГГММДД-XXXXX`), причиной уничтожения и точным таймштампом.
3. Данный акт доступен для аудита контролирующим органам (Роскомнадзор) и не подлежит удалению в течение 3 лет.
